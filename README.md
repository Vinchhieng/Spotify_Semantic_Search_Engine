# Vibe Search — Spotify Semantic Search Engine

A search engine over the [Spotify Million Song Dataset](https://www.kaggle.com/datasets/mrdatapsycho/spotify-million-song-dataset) (57,650 tracks) that finds songs by *vibe* ("melancholic acoustic ballad for a rainy morning") rather than by title or artist, using the lyrics as the only signal.

Built as **Option 1: Web Interface (FastAPI)**, and following the course's Milvus walkthrough: lyrics are chunked, embedded with a sentence-transformer, and indexed/searched in **Milvus** (via `pymilvus`'s embedded "Milvus Lite" — a single local `.db` file, no server to stand up).

## Project structure

```
spotify_search/
├── build_index.py        # one-off script: chunks, embeds, and indexes the dataset
├── search_engine.py       # core search logic: chunking, embedding, Milvus index + search
├── evaluate.py             # standalone: HNSW vs. exact-search Recall@K + latency comparison
├── app.py                 # FastAPI app (serves the UI + /api/search) — thin wrapper, no search logic of its own
├── requirements.txt
├── templates/
│   └── index.html
├── static/
│   ├── style.css
│   └── script.js
└── data/
    ├── spotify_vibes.db        # generated by build_index.py (Milvus Lite file)
    └── eval_embeddings.npz     # generated by build_index.py, used only by evaluate.py
```

**Separation of concerns:** `search_engine.py` is the entire core semantic-search pipeline (chunking → embedding → Milvus index/search) and has no knowledge of FastAPI or HTTP. `app.py` only imports `SemanticSearchEngine` and exposes it over HTTP — it contains no search logic itself. `evaluate.py` is a separate, optional tool that measures one part of `search_engine.py` (the HNSW index) against a ground-truth baseline; it isn't used by `app.py` and doesn't run as part of normal search requests.

## Getting started

```bash
# 1. install dependencies
pip install -r requirements.txt

# 2. put spotify_millsongdata.csv in this folder

# 3a. quick smoke test on a small sample first (~2-3 min)
python build_index.py spotify_millsongdata.csv --sample 2000

# 3b. once that looks right, build the full index
#     (~400k lyric chunks; mpnet-base-v2 is a larger model than MiniLM, so
#      this takes longer on CPU than a smaller-model build — budget more
#      time, or use a GPU if you have one)
python build_index.py spotify_millsongdata.csv

# 4. run the app
uvicorn app:app --reload

# 5. (optional) compare HNSW against an exact-search baseline
python evaluate.py
```

Then open **http://127.0.0.1:8000**. Rebuilding is only needed when the dataset or chunking/embedding logic changes — `app.py` just connects to the existing `data/spotify_vibes.db` at startup.

`build_index.py` drops and recreates the Milvus collection on every run, so changing `EMBEDDING_DIM` (e.g. from a different embedding model) is handled automatically the next time you rebuild — no separate migration step.

> **Note (Windows):** Milvus Lite (the embedded/serverless mode used by `MilvusClient("path/to.db")`) currently only ships for Linux and macOS. On Windows, run a local Milvus server via Docker instead and point `MilvusClient` at `http://localhost:19530` — everything else in `search_engine.py` stays the same.

## Technical architecture & discussion

### 1. Embedding dimension & representation

**Model: `sentence-transformers/all-mpnet-base-v2` → 768-dimensional embeddings.**

This is a larger, higher-quality sentence-embedding model than a MiniLM-class model — 12 transformer layers vs. 6, 768-dim vs. 384-dim output. It costs more to encode (roughly 5x the parameters), but produces embeddings generally considered the strongest all-round option in the Sentence-Transformers library, which matters here because "vibe" queries rely on abstract, paraphrase-level semantic matching rather than shared vocabulary — exactly where a stronger encoder helps most.

**Chunking by stanza, not whole-lyric embedding.** Each song's lyrics are split at the blank lines that already separate verses/choruses in the raw lyric sheet — the natural unit where a song's "vibe" actually lives — rather than encoded as one vector for the whole song:

- A single embedding for an entire lyric sheet averages every line together, so a song that's 90% verse and one chorus expressing the target "vibe" gets diluted into an embedding that doesn't clearly represent that vibe.
- A verse or chorus is a coherent thought the songwriter already delimited; splitting there gives cleaner chunk boundaries than an arbitrary character-count cut mid-line, which is what a naive fixed-length splitter would do.
- Two guardrails handle the real edge cases found in the data: stanzas over ~400 characters (songs formatted with little/no blank-line structure) get sub-split by grouping their complete lines up to ~220 characters; stanzas under ~30 characters (a stray one-word ad-lib, a formatting artifact) get merged with a neighboring chunk so no near-empty, low-signal chunk gets indexed on its own.
- Tested on the real dataset: this produces **~6.9 stanza-based chunks/song on average** (~157 characters/chunk, ranging 30–424 chars after the guardrails), or roughly **400,000 chunks total** across all 57,650 songs — the actual number of vectors indexed in Milvus.
- At query time, results are aggregated back from chunk → song: a query searches over chunks, then each song keeps only its single best-matching chunk (as both its score and its displayed excerpt), so multi-chunk songs don't crowd out other results.

### 2. Similarity measure

**Cosine similarity** (`metric_type="COSINE"` in Milvus), on embeddings L2-normalized at encode time (`normalize_embeddings=True`).

Per the slides' own decision rule — *"Is the embedding vector normalized? Yes → cosine similarity, No → Euclidean distance"* — Sentence-Transformers embeddings are explicitly normalized here, so cosine is the correct choice. More fundamentally, cosine similarity measures the *angle* between two embeddings rather than their absolute position/magnitude in space, which matches what we actually want: two lyric chunks expressing the same mood should be considered similar regardless of how "intense" or long the phrasing is. Euclidean distance would additionally penalize differences in vector magnitude that aren't semantically meaningful here.

### 3. Indexing strategy

**HNSW** (Hierarchical Navigable Small World graph), via `index_params.add_index(index_type="HNSW", metric_type="COSINE", params={"M": 16, "efConstruction": 64})`.

HNSW is an **approximate** nearest-neighbor index, not an exact one — it's fundamentally a speed-for-recall trade-off, not a strictly-better option. Referencing the trade-off table from the slides:

| Method | Fit here? |
|---|---|
| **Flat (exact)** | 100% accurate by definition (it *is* the ground truth every ANN index is measured against), but scans every one of ~400k vectors per query |
| **IVF_FLAT** | Faster than flat by only searching the nearest cluster(s), but can miss chunks that land near a cluster boundary — a real risk when many chunks are short/ambiguous lyric fragments |
| **HNSW** | Builds a navigable graph for fast approximate search; recall depends on its parameters (`M`, `efConstruction`, query-time `ef`) and the data, not a fixed guarantee |

HNSW was chosen because at this dataset's scale (~400k vectors) it's a well-established default that gets most of exact search's accuracy at a fraction of the query cost — but "most of the accuracy" is a claim worth actually measuring rather than assuming. That's what `evaluate.py` is for: it runs the *same queries* through both Milvus's HNSW index and a brute-force exact cosine search over the full vector set (cached at build time in `data/eval_embeddings.npz`), and reports:

- **Recall@K** — the fraction of the exact top-K chunk IDs that HNSW's top-K also contains, averaged across a fixed query set. This is the actual, computed cost of using an approximate index instead of an exact one — not an assumed percentage.
- **Latency** — average wall-clock time per query for each method, so the speed side of the trade-off is measured too, not just asserted.

Run it yourself with `python evaluate.py` after building the index; it prints a table (`K`, `Recall@K`, `HNSW ms`, `Exact ms`, `Speedup`) computed from real search calls against your own built index, not pre-filled numbers.

Query-time search depth is controlled by `search_params={"params": {"ef": 96}}` in `search_engine.py` — a higher `ef` trades some latency for more thorough graph traversal (typically better recall). If `evaluate.py` shows recall lower than you want for your use case, raising `ef` (in both `search_engine.py` and `evaluate.py`'s `hnsw_search`) is the first lever to pull, at the cost of slower queries.

## Limitations & possible extensions

- Stanza splitting relies on the blank-line formatting already present in the source lyrics; a song transcribed with no blank lines at all falls back entirely to the sub-splitter (line-grouping), which loses the structural benefit for that one song.
- Repeated choruses generate near-duplicate chunks; this doesn't hurt result quality (aggregation already keeps one hit per song) but does mean some indexing time is spent on redundant vectors.
- `evaluate.py`'s query set is a fixed list of 10 hand-written vibe queries. That's enough to characterize the recall/latency trade-off directionally, but a larger and/or randomly sampled query set would give a tighter estimate — increase `--queries` or extend `DEFAULT_QUERIES` if you want more statistical confidence.
- No reranking stage: results are ranked purely by the HNSW/cosine score from the initial retrieval, by design — this project intentionally keeps the pipeline to chunking → embedding → ANN search → aggregation, without adding a cross-encoder reranker, RAG, or an LLM API call on top.
